# 협업 컨벤션 (4K)

> 김기엽님 제안 컨벤션(10/29) 기반. 해커톤 일정에 맞게 "채택 우선순위 4가지"를 필수로, 나머지는 권장으로 둡니다.

## 필수 4가지
1. `main`에 직접 커밋하지 않기 (룰셋으로 막혀 있음)
2. 작업마다 Issue와 브랜치 만들기
3. PR에 변경 사항과 확인 방법 적기
4. 최소 1명 리뷰 승인 후 병합 (작성자 본인 승인 불가)

## 작업 흐름
```
Issue → 브랜치 → 작업 → PR → (다른 AI로 유닛 테스트) → 리뷰 → 병합 → 실제 사용 확인
```
- 작업 시작/완료는 Discord 작업 채널에도 한 줄 남깁니다. (`#12 연결 엔진 시작합니다` / `#12 PR 올렸어요`)
- 문구 오타처럼 영향이 아주 작은 수정은 PR 하나에 모아도 됩니다.

## 브랜치
`<종류>/<이슈번호>-<짧은-설명>`

| 종류 | 용도 | 예시 |
|---|---|---|
| feat | 기능 추가 | `feat/12-profile-card` |
| fix | 버그 수정 | `fix/15-ocr-empty-box` |
| refactor | 구조 개선 | `refactor/20-engine-split` |
| docs | 문서 | `docs/3-readme-run` |
| test | 테스트 | `test/18-engine-cases` |
| chore | 설정·정리 | `chore/1-repo-setup` |

## 커밋
`<종류>: <변경 내용>` (제목 50자 안팎, 한 커밋엔 한 목적)
```
feat: 게시물 간 이름 단서 연결 로직 추가
fix: 빈 캡션에서 발생하는 오류 수정
docs: GPU 서버 접속 방법 추가
```
금지: `수정`, `작업 완료`, `최종`, `update`, `wip`, `fix`처럼 무엇을 바꿨는지 모르는 제목.

## Issue
목표 · 배경 · 완료 조건 · 확인 방법 · 담당/검토자/우선순위 (템플릿 사용). 완료 조건을 못 쓰겠으면 더 작게 나눕니다.

## PR
- 제목은 커밋 규칙과 같게, 본문에 `Closes #번호`.
- 병합 방식은 **Squash merge** 권장 (PR 제목이 main 커밋 한 줄이 됨).
- 한 사람이 검토할 수 있는 크기로 나눕니다.

## 리뷰
- 검토자: **이슈 담당자 + 관련자 1명**이 원칙, 마감이 급하면 1명 승인으로 병합.
- "좋아요"만 남기지 않고, 확인한 동작이나 남은 우려를 적습니다.
- 공통 구조(`schemas/`, JSON 계약) 변경은 팀 채널에 공유 후 병합.
- `main`에는 실행 가능한 코드만 들어갑니다.

## AI 활용 규칙
- AI에게 목표 · 수정 범위 · 완료 조건을 먼저 줍니다. 요청 안 한 파일/기능을 건드리지 않게 지시합니다.
- 계획은 상위 모델, 단위 구현은 중간급 모델, 유닛 테스트는 **구현과 맥락을 공유하지 않는 다른 AI**로.
- **작성자가 설명할 수 없는 코드는 병합하지 않습니다.**

## 실제 사용 확인
병합 후 사람이 부모 입장에서 UC1·UC2 흐름을 직접 써 보고, 문제는 새 Issue로 남깁니다.

## 충돌 대응
충돌 발견 → 팀 채널 공유 → 관련 파일 담당자가 해결 → PR 본문에 해결 내용 기록.
